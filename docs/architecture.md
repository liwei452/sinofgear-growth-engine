# SinofGear Growth Engine Architecture

## System shape

SinofGear Growth Engine is a same-origin Vue and Django application for an organization-scoped content growth workflow. The Vue 3 client uses Vue Router and TanStack Query. Django REST Framework owns the `/api/v1` contract and PostgreSQL is the system of record. Celery workers and beat use Redis for queued AI/content/publishing work. MinIO stores private asset binaries; API endpoints issue validated, short-lived download URLs rather than exposing storage credentials.

The backend is split by domain: identity and permissions, platforms and credentials, knowledge ontology, products, assets, campaigns and briefs, jobs and AI runs, reviewed content, publishing, and privacy-preserving tracking analytics. Services enforce organization identity and state transitions beneath the API views. External AI, storage, and publishing connectors sit behind integration interfaces so tests can use deterministic local implementations.

## Request and security boundary

The browser authenticates with Django's session cookie. Every API request includes credentials. Before a non-safe method (`POST`, `PUT`, `PATCH`, or `DELETE`), the frontend obtains a CSRF cookie from `GET /api/v1/auth/csrf` when needed and sends its value in `X-CSRFToken`. Login itself is CSRF protected. A client must not disable these checks or send credentials to a different origin.

Backend permission classes resolve one active membership, attach its organization to the request, and require the domain-specific permission. Querysets and service checks scope records to that organization; identifiers from another organization are not an authorization shortcut. Read and manage permissions remain separate, including publishing and tracking. Connector secrets are write-only and are not returned by serializers, cached in query data, or represented in generated response types.

JSON errors from mutation responses have one recoverable envelope:

- `code`: stable machine-readable category or HTTP fallback code.
- `message`: safe user-facing explanation.
- `recovery_action`: a concrete next step.

Domain details such as `errors`, `detail`, or `current_version` may accompany the envelope. The renderer adds the three required fields to manual and framework-generated mutation errors and replaces server-error prose with a generic message. The frontend maps field errors to forms, never renders server stacks or arbitrary objects, and uses fixed safe messaging for 5xx responses.

## OpenAPI contract and generated types

`GET /api/v1/schema` is the canonical OpenAPI 3 contract. Operations use explicit resource tags, including separate knowledge concept/relation, master/platform content, publishing, tracking, and authentication groups. Every mutation documents JSON errors that include `code`, `message`, and `recovery_action`. Backend contract tests also verify that every local component reference resolves and that method-field types match runtime values.

Generated TypeScript lives in `frontend/src/api/generated/schema.ts` and must not be edited by hand. The generator is pinned exactly in `frontend/package.json` and `frontend/pnpm-lock.yaml`.

From `frontend`:

```text
pnpm api:generate
pnpm api:check
```

Both commands export the schema directly with Django's test settings and then run the local `openapi-typescript` package. They do not require a development server. Export and generation happen in an operating-system temporary directory. `api:generate` writes the checked artifact; `api:check` compares generated bytes without changing the workspace and exits non-zero on drift. The export has no server URL, build timestamp, secret, or environment-specific credential.

## User interface

The frontend is a novice-facing Chinese operations workspace. It groups navigation by business task, keeps one obvious primary action per page, and provides loading, empty, error, and recovery states. Modal operations use the shared focus-trapped dialog behavior. Query keys include organization and filter identity, while cursor and polling flows isolate stale asynchronous generations.

The interface exposes approved knowledge, products, assets, content review, publishing status, and aggregate analytics. It does not expose raw click events, IP addresses, privacy hashes, connector secrets, or unrestricted JSON editors. Publishing eligibility and tracking provenance are revalidated against canonical backend state immediately before sensitive mutations.

## Deployment topology

The local Compose topology runs frontend, API, worker, beat, PostgreSQL, Redis, and MinIO services. Only the frontend and API are intended as application entry points; infrastructure credentials come from environment configuration and production values must differ from development examples. Database migrations are the schema-change mechanism, and API/type drift checks run alongside backend tests, frontend tests, lint, type-check, and production build gates.

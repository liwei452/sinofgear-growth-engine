# 一键多渠道发布设计

日期：2026-08-14  
状态：已确认，待实现

## 目标

让工厂老板在审核完推广内容后，只需点击一次“发布到已连接渠道”，即可把已批准内容提交到 LinkedIn Company Page、Facebook Page、Instagram Business 和 TikTok。系统负责渠道校验、任务编排、防重复、失败隔离、重试与结果回填；普通用户不需要理解 Connector、PublishTask、OAuth Scope 或 API。

首期仍使用 Fake Connector 验证完整闭环，不冒充真实发布。真实连接器只有在用户另行授权 OAuth、密钥及平台审核权限后才允许启用。

## 用户体验

“推广”页继续保持当前极简信息架构。每个渠道内容卡展示内容摘要、审核状态和账号连接状态，但不显示技术字段。

当至少一个渠道满足“内容已批准、账号已连接、连接器具备发布能力”时，页面底部显示唯一主按钮“发布到已连接渠道”。按钮旁用普通语言列出本次将发布的平台；不满足条件的平台显示明确原因并自动排除。

用户点击主按钮即表达本次真实发布意图。系统不再增加第二个确认弹窗，但只允许已批准内容进入发布任务。重复点击同一个发布批次不会产生重复帖子。

提交后，页面原位显示渠道级结果：

- 等待发布：任务已安全入队。
- 发布中：平台正在处理。
- 发布成功：显示发布时间和平台帖子链接。
- 发布失败：显示可理解的原因，并提供“重试失败渠道”。
- 尚未连接：显示“连接账号后可发布”，不伪装成功。

“下载发布包”保留为次要兜底操作，不能与真实发布主按钮争夺视觉层级。

## 发布批次

新增面向增长工作区的发布批次边界。一个批次记录操作者、组织、创建时间、不可变的渠道内容快照、所选渠道、幂等键和汇总状态。每个渠道对应一个独立批次项目，并绑定现有发布任务或明确的不可发布原因。

批次汇总状态只反映整体进度，不覆盖渠道结果：

- `QUEUED`：至少一个渠道已入队，尚未开始。
- `RUNNING`：至少一个渠道正在发布。
- `PARTIAL_SUCCESS`：有成功，也有失败或跳过。
- `SUCCEEDED`：所有入选渠道均成功。
- `FAILED`：所有已尝试渠道均失败。
- `CONFIGURATION_REQUIRED`：没有任何渠道可发布。

渠道项目状态使用现有发布任务语义，并额外允许 `SKIPPED`。一个渠道失败不会回滚其他渠道已经成功的帖子。

## 服务边界与数据流

前端只调用一个增长工作区批量端点，并提交当前页面展示的渠道包 ID。后端按当前登录组织重新读取并锁定数据，不能信任前端提交的批准状态、账号、平台或内容。

后端依次执行：

1. 校验所有渠道包属于当前组织且是当前版本。
2. 只接受 `APPROVED` 内容包，并生成不可变发布快照。
3. 为每个平台选择唯一、已启用且能力匹配的官方账号连接。
4. 为可发布渠道创建现有 `PublishTask`；为不可发布渠道记录具体原因。
5. 使用客户端幂等键和服务端内容指纹防止重复创建批次或帖子。
6. 返回整个批次及渠道状态，前端通过轻量轮询刷新结果。

建议接口：

- `POST /api/v1/growth/publish-batches`：创建或复用一键发布批次。
- `GET /api/v1/growth/publish-batches/{id}`：读取批次和渠道结果。
- `POST /api/v1/growth/publish-batches/{id}/retry-failed`：只重试失败且仍满足发布条件的渠道。

真实连接器继续通过现有发布服务调用，不在增长模块复制平台 API 逻辑。Fake Connector 在测试环境返回明确的 `SIMULATED_SUCCEEDED` 结果和假帖子 URL；非测试环境不得把模拟结果标记为真实成功。

## 账号与连接器门槛

每个真实渠道必须同时满足：

- 用户已明确授权官方 OAuth 或平台要求的合法凭据。
- 连接器能力声明包含对应内容类型的发布能力。
- 必需权限范围已由平台和用户授予。
- 账号类型符合平台要求，例如企业主页或商业账号。
- 凭据未过期，且连接器最近一次健康检查通过。

禁止使用密码、Cookie、浏览器会话、验证码或未许可抓取方式绕过官方接口。TikTok 与 Instagram 是一等渠道，不因接入难度降级为仅下载渠道。

## 错误处理与重试

平台限流、临时网络错误和可恢复的服务错误进入安全重试；权限撤销、内容违规、账号类型不符等不可恢复错误立即失败并给出操作建议。所有重试复用同一渠道项目和发布指纹，不能生成重复帖子。

“重试失败渠道”只处理失败项目，不重新发布成功项目。若连接器返回外部帖子 ID 后本地写入失败，恢复流程必须先按幂等引用查询或对账，不能盲目再次发布。

## 审计与指标

发布批次保存人工批准人、发起人、内容版本、连接器能力快照、渠道结果、外部帖子 ID、平台 URL、失败分类和尝试时间线。成功结果自动进入现有效果记录；仍支持手工回填无法通过官方 API 获取的指标。

普通页面只显示用户能采取行动的信息。完整技术审计记录保留在后端，不暴露到工厂老板的主界面。

## Fake Connector 验收

本地 MVP 必须证明以下行为：

- 一次点击为四个已批准且模拟连接的渠道创建一个发布批次。
- 每个渠道有独立结果，单渠道失败不会阻断其他渠道。
- 重复提交相同幂等键不会新增批次或重复帖子。
- 重试只触发失败渠道。
- 未批准内容、跨组织内容和未连接账号不能发布。
- UI 明确标识“Demo / Fake 发布结果”，绝不伪装成真实平台帖子。
- 下载发布包仍可使用，但降级为次要操作。

## 真实接入边界

本阶段不索取、不保存真实 OAuth 凭据，不调用真实社媒发布接口。进入真实渠道接入时，需要用户分别确认账号授权、平台应用、权限范围和密钥配置；每个连接器通过契约测试、安全审查和沙盒发布验证后，才可把主按钮从 Demo 模式切换为真实发布模式。

# 四渠道手工发布包设计

日期：2026-08-15  
状态：产品审核已批准

## 目标与边界

当 LinkedIn、Facebook、Instagram、TikTok 四个当前版本内容包均已人工批准时，用户可一次下载一个本地 ZIP，随后人工登录各平台发布。导出不调用平台、不写外部系统，也不读取或包含账号凭据。

## 方案

后端接收四个内容包 ID，并按当前组织重新读取和校验：渠道完整且唯一、状态为 `APPROVED`、来源平台内容仍是最新版本。任何缺项、未批准、旧版本或跨组织选择均拒绝，不信任前端状态。

导出使用 Python 标准库在内存中生成确定性 ZIP，不新增持久化模型。相同批准版本生成相同规范化文件、固定 ZIP 元数据和相同 SHA-256 内容哈希；内容修订后会产生新的待审版本，重新批准前不得导出。压缩包设置严格的文件数、单字段长度和总大小上限。

ZIP 结构：

```text
four-channel-manual-publishing-package.zip
├── manifest.json
├── linkedin/
│   ├── content.json
│   ├── evidence.json
│   └── assets.json
├── facebook/...
├── instagram/...
└── tiktok/...
```

`content.json` 保存平台文案、标题、标签、CTA、UTM，以及 TikTok 的脚本、分镜、口播、字幕和 9:16 规范。`evidence.json` 只保存已随批准内容固化的事实摘要。`assets.json` 只保存素材原文件名、类型、大小和校验和等公开引用，不保存对象存储键、磁盘路径或下载凭据。`manifest.json` 保存结构版本、渠道文件清单、Demo/Fake 标识、人工发布说明和内容哈希。

## 用户体验

推广页保留一个次要主动作“下载四渠道手工发布包”。只有四渠道均有当前且已批准内容时可用；否则按钮禁用并用普通语言列出需要补齐或重新审核的渠道。下载成功后明确提示“仅本地导出，未发布到任何平台”。刷新后可用性由服务端已批准状态恢复。

## 验证

后端覆盖完整导出、未批准、缺渠道、跨组织、旧版本、确定性哈希、安全字段与大小限制。前端覆盖按钮门槛、一次下载、错误提示和不触发发布接口；浏览器链路覆盖刷新后的批准状态与本地下载。
